Start here — order of operations

  1. Period table: first visit scans Firestore (log shows detail); later visits can use cached earliest date. Load all periods / Clear saved scan as needed.
  2. A + B (once each): Migrate employees, then payments — master data is not tied to a single pay period (payment doc ids already embed periodId).
  3. C (per period): Migrate attendance using the table — each row is one pay period’s date range. Use one row to test, then all periods when ready.
  4. Refresh status reloads badges. Optional: flat payment_confirmations_v2 import at the bottom.

What each step does

A · once
Employees Legacy employees → employees_v2 (full doc merge). Admin uses top-level rates when there is no rateHistory row for a period.
B · once
Payments All payment_confirmations in one pass: id {employeeId}_{start}_{end} → payroll_periods_v2/{periodId}/payments/{employeeId}.
C · per period
Attendance Legacy attendance/…/dates in that period’s range → attendance_v2. Smart mode (default): compares each day to v2; if different, backs up both snapshots + merged result to migration_v2_attendance_diffs, then merges clockIn/clockOut by newer timestamp per half (tie → v2). v2-only days in range are untouched.
